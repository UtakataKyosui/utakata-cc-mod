# clarify-fix-request

修正・変更の依頼を受けたとき、何をどう直すかが決まるまでファイルの編集を止める。依頼文だけで決まらない点があれば、推測で直さず AskUserQuestion で聞き返させる。

修正して OK をもらったあとに「あれ、こうだっけ」と言われるのは、依頼の解釈を確かめないまま直し、完了報告でも解釈を示していないときに起きる。この Mod は直す前の確認と、完了報告での解釈の明示を求める。

| 場面 | 仕組み |
|---|---|
| 修正依頼のプロンプトが届いた | 編集を止める。ステータスに「修正内容: 未確認」を出す |
| 依頼文だけで決まらない点がある | `AskUserQuestion` で聞く。回答が返ると編集を解禁する |
| 依頼文だけで決まる | `confirm_fix_request` ツールに、依頼文の引用・対象・今の状態・直した後の状態・決まっていない点を書く。決まっていない点が空で、引用が依頼文と一致すれば編集を解禁する |
| 完了報告 | 依頼の言葉、確認した解釈、変更前→変更後を並べるよう、システムプロンプトで指示する |

- 修正依頼かどうかは、プロンプトに「直して」「修正」「変えて」「戻して」「調整」「小さく」「ずれ」「指摘」「fix」などの語が含まれるかで判定する。誤って修正依頼と判定しても、`confirm_fix_request` を 1 回呼べば先へ進める。
- 止めるのは `Edit` / `MultiEdit` / `Write` / `NotebookEdit` と、ファイルを書き換える Bash。Bash は、コマンドの位置にある `sed -i`、`perl -i`、`tee`、`patch`、`git apply` / `restore` / `checkout --` と、ファイルへのリダイレクト（`>`、`>>`、`1>`、`2>`、`&>`）で判定する。引用符の中身とヒアドキュメントの本文は判定に使わないため、`rg patch src` や `cat src/patch.ts` のような読み取りや調査は止めない。`2>&1` や `/dev/null` への出力も止めない。
- 利用者が送ったプロンプトだけを見る。バックグラウンドタスクの通知や自動継続のプロンプトでは状態を変えない。修正依頼でないプロンプトが届くと、未確認の状態は解除される。
- サブエージェントの編集も止める。サブエージェントは利用者に聞けないため、決まっていない点を親のエージェントに返すよう伝える。

## 導入

```
/plugin install clarify-fix-request@utakata-cc-mod
```

## 制約

依頼が曖昧かどうかはモデルが `confirm_fix_request` に書く内容で判断しており、モデルが決まっていない点を書かなければ聞き返しは起きない。引用が依頼文に含まれるかは検査するが、引用から直した後の状態が導けるかまでは検査しない。

修正依頼の判定は語の一致で行うため、語を含まない言い回し（「ここ赤がいい」など）では止まらない。その場合もシステムプロンプトの指示は効く。
